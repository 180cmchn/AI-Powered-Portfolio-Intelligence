## 根因与变更范围

此前 `correct_snapshot()` 总是把整份 holdings 交给 `_replace_ledger_positions()`。该方法适用于建立期初基线，但回传 holdings 没有交易批次、原可卖日期和费用依据，所以现金校正也会重建所有证券。原 API `CorrectionHolding(HoldingInput)` 又先按最多六位小数验证全部单位成本，正常交易生成的循环小数甚至还没到 Store 就被拒绝。

现在 `_correction()` 从现存精确 positions 构造字段级差异，不在预览期间写入。不存在于变更列表的证券以及数值等价的字段保持原事实；现金或可卖校正还保留原 holdings 行序、零数量行及单位成本字符串，避免意外改变研究范围；`_replace_ledger_positions()` 只保留期初建立用途。最终提交仍使用原事务：账本、现金、账户版本、快照、需求、任务和操作回执一起提交。未改变证券的 `ledger_positions.body` 在测试中按完整原始字符串断言相同。

全量回归曾发现四个历史测试仅要求无关持仓校正把现金字符串 `10000` 格式化为 `10000.00`。本轮按未改事实保持原值的契约，改为同时断言前后现金字符串完全相同和 Decimal 数值仍为 `10000.00`；原估值、账户版本、任务与隔离断言均保留。

没有新增表、schema 迁移、历史回填或数据库修补。未扫描历史 correction，也不猜测此前丢失批次原本的生效日期。

## 校正操作契约

高级校正使用 `POST /api/accounts/{id}/corrections/preview`，确认使用同路径去掉 `/preview`。两者使用相同输入；预览返回账户版本、现金前后值、每项精确前后 position、字段列表、影响说明、原因、操作者和 `preview_token`。确认携带该 token；更改输入、账户版本、账户身份或上海生效日期都会拒绝旧预览。原有客户端允许不带 token 的普通 patch；新界面始终先预览。新 HTTP 完整快照 `mode:snapshot` 必须明确提交 holdings，且确认时强制要求 preview_token，预览会列出遗漏证券清仓的差异；日常界面使用默认 `mode:patch`。

- `cash` 缺省：保留；`null`：明确未知；`"0"`：已知为零。改变现金仍要求最多两位小数。
- `holdings` 缺省或 patch 空列表：保留所有持仓。只列证券 A 不影响 B/C。
- 单行缺省 `quantity`、`cost_price`、`total_cost`、`available_quantity`：保持对应事实。新证券必须提供数量，未填成本和可卖依据保持未知。
- `cost_price:null` 或 `total_cost:null`：明确成本未知；`"0"` 是已知零成本。单位成本和剩余总成本不能同时提供。
- 新成本输入仍最多六位小数、非负、有界、有限。API 仅对返回值做最多 80 字符、60 位的小数比较；只有数值等于既有派生单位成本或精确剩余总成本时才能复用，不把这种比较能力变成新输入的无限精度许可。
- 成本数值相同（例如 10.0 / 10.00）时，保留权威剩余总成本，绝不先舍入单位成本再乘数量。只改成本时保留原可卖批次。
- 数量增加时保留原 lots，增量为未知可卖；数量减少但未给批次依据时，预览明确提示剩余可卖范围转为未知，不能任意猜测 FIFO 或其他历史批次。精确总成本继续保留，直到用户明确校正成本。
- `remove:true` 是明确移除持仓行（包括原本就是零数量的行）；预览标明 `holding_removed`，行退出账户研究范围，原账本与历史流水保留。不能同时提供非零数量、成本或可卖依据。单纯原样回传 `quantity:"0"` 继续保留原零行，不猜测删除意图。
- 对原非零持仓，`quantity:"0"` 是清仓校正：剩余总成本归零、lots 清空；不扣现金、不创造成交或已实现盈亏。清仓后重新校正为非零数量而未填成本，成本重新为未知，不能把此前清仓的零当作新持仓成本。
- `available_quantity:null` 明确清除可卖依据；数值相同的已知可卖量保持原历史 dates。新增可卖事实仅从当前上海日期生效，不倒推过去。对完全未知批次明确确认 `"0"` 时，保存带当日日期的 `availability_confirmation`，与缺省或明确未知可区分；不虚构未来解锁日。
- 无事实变化的确认返回 422“没有账本事实变化，无需重复校正”，不新增流水、账户版本或研究任务。

旧 `PUT /api/accounts/{id}` 保留显式 `ledger_action:correction` 与依据的兼容约束，明确提交的完整 holdings 仍是完整快照语义，缺省 holdings 保留原列表，显式 `[]` 清仓并移除原零数量行；缺省 cash 保留，显式 null 为未知；单行缺省 cost_price 保留精确成本，显式 null 才清除。适配器按字段数值比较保留未改证券，允许系统派生长单位成本原样返回，新的成本变更仍受六位校验。正常新界面不使用旧全量入口。兼容入口在证券解析前保存原字段集合，防止 resolver 的 model_copy 把缺省 holdings 标为已填；操作指纹以原始稀疏意图计算，再在 Store 的 CAS 事务内补足未改字段。相同操作 ID 改为显式 null 会冲突；代码别名重复行若缺省/显式成本意图不同，会拒绝合并。旧调用方若想清仓，须明确其完整快照意图；新调用方应采用稀疏 patch 并预览差异：非零持仓清仓用 `quantity:0`；删除原零数量行或明确移出持仓范围用 `remove:true`。旧 PUT 的同值保存仍沿用兼容保存流程，前述无事实变化返回 422 的契约适用于新 corrections API。

`operation_id` 回执查询/重放先于版本检查，原响应丢失可只读取回。重复同操作不再次记账；同 ID 换内容、过期版本、另一账户、失效预览均被拒绝。测试在队列提交前注入异常，验证全部事实、需求、流水和回执一起回滚。校正仅形成一个账户输入版本和一项真实需求，由原生产去抖机制合并到最新任务。

收尾复审额外发现旧 PUT 的 Pydantic 默认值仍会把缺省字段转换成 `None`/`[]`。实际新增 6 项生产 HTTP 回归在修正前全部失败（循环成本被清成未知、缺省 holdings 清仓、缺省 cash 变未知等），修正后全部通过。证据：[修正前](ledger-legacy-omission-before.txt)、[修正后](ledger-legacy-omission-after.txt)。这些是本轮候选实现的后续发现，不能隐去，也不以先前通过的整组代替最终验证。

## 成本、费用与研究输入

`metrics()` 继续取账本精确 `total_cost`，单位成本只作派生展示。新增说明区分交易成本与期初/迁移/明确校正成本；已记录买入费用计入对应剩余成本，无法证明期初或校正费用的包含范围时保留未知。未实现盈亏没有估算未来卖出费用；已实现盈亏已计本次卖出费用和结转成本，累计费用用于核对，不再从盈亏或权益扣第二次。账户研究上下文不再统一宣称全部成本已含费用，逐证券依据仍原样提供。没有改写历史报告、预测或评分。

覆盖的精确测试包括真实多笔买入形成循环成本、部分卖出形成循环剩余总成本、现金/无关证券校正、末笔费用更正和撤销、最后清仓、已知未知成本混合、高位总金额、零成本/零数量、缺省/未知/零可卖、同值无操作、CAS、幂等、账户隔离、日期失效和原子回滚。部分卖出断言完整 `cost_relieved`、`total_cost` 与 `realized_pnl_effect`，不是只比较页面四舍五入金额。

## 现存受影响数据

此次修复只保护后续明确校正。已发生的旧校正可能是用户有意重建期初；不能将其一概认定为现金操作。若怀疑某条旧记录丢失可卖或费用依据，先只读核对该条不可变流水中的 `before_positions`、`after_positions`、当时输入、原因及实际交割材料。只有可证明的前后事实并经用户确认，才能追加一条有依据的新校正；新确认可卖仍仅从当前上海日期生效。不能改写原流水，也不能根据如今可卖反推过去日期。日常库部署/修复仍按既有实例身份、备份和升级确认流程单独执行。
