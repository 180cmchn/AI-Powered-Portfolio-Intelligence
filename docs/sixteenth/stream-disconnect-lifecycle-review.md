# 第十六轮真实断流：任务生命周期只读复核

**根因尚未确定。** 五次历史断流具有很接近的字节空闲间隔：最后一个 HTTP 字节之后约 50 秒出现 `RemoteProtocolError`。已检查的应用调度、截止和清理路径，没有显示这些请求被任务替换、总时限或正常停机提前取消。现有证据不能把责任归给供应商，也不能据此确定本机代理或某个网络节点。

本复核读取独立 SQLite（`mode=ro`）、生命周期日志及冻结源码 `b7afd9860b14304d6c1f698e7fbaed5db80435d37c6f90db920000324c806470`；没有启动模型、重试未知请求、修改配置/数据库或重启服务。[机器记录](stream-disconnect-lifecycle-review.json) 保存请求边界、时间、任务身份、依赖与被检查文件的哈希。最初复核了四项，随后追加正常配置任务的独立第五次失败；各任务内容评估仍分别保存。

五项均先收到 HTTP 200，再在响应体中途发生错误；没有有效协议终止、HTTP EOF 或 `cancelled_by`。首次有效事件阈值为90秒，语义空闲阈值300秒，单请求硬限900秒；各请求已取得有效事件，失败时语义空闲约51.49—88.49秒，尚未达到应用限时。HTTPX 的网络 `read` 显式设为 `None`。心跳字节会推进 `stream_last_byte_ms`，未必推进语义进度，因此两类空闲不可混称。HTTPX 官方文档将读超时与协议错误列为不同异常类别，但异常名称本身不提供多跳连接关闭方向。[超时说明](https://www.python-httpx.org/advanced/timeouts/)、[异常类别](https://www.python-httpx.org/exceptions/)。

任务先后顺序也不支持“新任务先取消旧任务”的解释。A v5 于23:38:12.184终态失败，新的 universe 任务在6.591秒之后才创建；universe 于23:48:05.490失败，公共材料任务在0.461秒之后创建；公共材料于次日00:02:00.257失败，配置任务在6.529秒之后创建。受影响的五个 A 任务都没有持久取消记录。事件595的输入版本替换属于 B v1→v2，不能套到 A v5 上。生命周期日志首次 stop 是00:15:42.846，晚于最后配置任务00:15:35.163失败7.683秒；随后才正常 start/stop 验证重启。五次失败之前没有 stop/restart。

源码中的关闭路径如下。

- `Service.tick` 看到任务持久状态不再为 `running` 才取消活动协程；`Service.stop` 使用 `service_shutdown` 原因取消并等待任务。实际受影响任务先记录传输错误，再变成 failed。
- 研究前的配置检查构造并关闭自己的临时 `ModelClient`，之后的研究使用另一个客户端。正常角色团队为子角色创建独立客户端，没有发现该失败子角色提前关闭经理客户端的共享路径。
- `TeamRunner.run` 在经理循环返回或抛出异常后进入 `finally -> close`。该清理先取消并等待剩余子协程，再关闭各角色客户端。因此失败后的 `aclose` 不能自动解释为失败原因。
- 模型请求的应用时限和 `CancelledError` 分支会记录 `cancelled_by` 与本地关闭原因。当前五项进入的是 `httpx.RequestError/RemoteProtocolError` 分支。有效终止后的可选尾流清理要求先解析到 terminal；五项没有 terminal，不适用这个分支。
- 已安装 httpcore 的 HTTP/1.1 接收层可在未完整响应时收到 EOF 并产生协议错误；响应迭代器在异常之后清理连接并重抛。AnyIO 层的 `ClosedResourceError` 映射为 `ReadError`，正常取消不会直接由这个映射变成 `RemoteProtocolError`。所查路径没有配置50秒读取上限。

事件1423实际观察到成功 CONNECT；其他四项的单次请求追踪没有 CONNECT，也可能复用了既有连接，不能宣布它们物理直连。供应商所称“请求方断开”需要关联其具体请求日志：它描述供应商连接另一端消失，尚不能区分应用、系统、代理或中间层最先发起关闭。应用字段 `upstream_transport_error` 是当前分类名称，不能当作供应商责任认定。

下一条需要的证据是同一新诊断请求的 `task.cancel/aclose` 调用原因与调用栈、最后字节时刻、连接身份和 FIN/RST/TLS 关闭方向，以及供应商对应日志。历史五项没有这类方向证据，不能追溯补造。本复核保留“约50秒字节空闲的连接层关闭”作为可检验假设，未重放任何已接受但结果未知的付费请求。

## 补充：direct 出现另一种读取错误

新独立正常入口direct矩阵的公共材料任务 `0558397bd51145c5b6ad9d17a931fd29` 在2026-11-05 01:03:17.361失败。独立数据库 `sixteenth-normal-direct-v1/evaluation.sqlite3` 的事件1776是经理研究请求：HTTP 200、总时长203.729秒，`ReadError`，无terminal/EOF/取消原因；最后字节至失败只有**185.93毫秒**，最大语义空闲9.707秒。硬限900秒、语义空闲300秒和父任务期限都没有耗尽。

最后配置任务 `b13c7e3bab69415da25c92ea26768503` 又于01:10:53.103失败。direct数据库事件2019是经理汇总请求：HTTP 200、总时长249.806秒，`ReadError`，最后字节至失败**142.84毫秒**，语义最大空闲62.129秒，仍未达到idle300秒、hard900秒和父任务期限；无terminal/EOF/取消原因。

因此，五次environment的约50秒模式不能覆盖所有后来错误，也不能把direct描述成已解决全部断流。当前缺少底层关闭方向和调用栈，ReadError不能单独区分远端、系统或本机连接资源错误；后续配置任务在公共材料任务失败之后创建，也不是先发生的替换取消证据。机器记录以独立的 `additional_direct_failures` 两项保存数据库/事件/任务身份，避免把两个数据库的序号混用。原五条environment证据保留。读取中的HTTP/1.1连接进入ACTIVE时会将keepalive到期值清空，所查连接池代码也未提供“50秒自动淘汰活动请求”的证据。
