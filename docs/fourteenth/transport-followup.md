## 原四次故障的判断

现有证据不支持“项目自己的请求超时主动取消了第1、2、4次”，也不能仅凭供应商的 client_gone 就判定客户端代码有错。三次均在 HTTPX 接收正文时得到 RemoteProtocolError / incomplete_response_body，本地 cancelled_by 为空，没有触发首事件、流空闲、请求硬限或整轮限时。请求已经取得 HTTP200 并产生流事件；没有记录 tool_choice 参数被拒绝。

四次原始请求均有环境代理和 HTTP CONNECT 隧道记录。供应商看到的下游可能是中间代理；代理断开时，供应商可记 client_gone，应用同时看到对端断流。第1、2次最后字节后约50秒断开，总耗时又接近180秒，不能据此确定究竟是链路空闲限时、总时限还是其他原因。第4次距最后字节仅约80毫秒，更不能用同一个客户端空闲计时器解释。

## 已修补的项目问题

原接收器在取得 response.completed/incomplete 等完整终止事件后立即退出 HTTP 流，并把 response_body_received 标为真。这样可能在网关发送 HTTP chunked 结束标记前主动关连接；旧第3次记录甚至在终止事件之后出现 receive_response_body.failed。它是项目侧可确认的问题，但不解释第1、2、4次，因为那三次尚未收到终止事件。

现在完整终止事件到达后，最多等待1秒读完 HTTP 尾部，并提前让出最早请求/整轮/正式期限。不重新生成、不延长研究预算。HTTP EOF、可选收尾超时、尾部传输错误、本地取消和终止前断流分开记录；协议完整和HTTP正文完整也分别统计。已收到完整终止对象时，尾部异常只记录，不把完整对象变成半截输出；未收到终止事件时仍失败，不拼接半截函数、不自动重发未知结果。

响应ID从 response.created 起即安全保存，便于将断流请求与供应商后台匹配；incomplete_details.reason只保留有限格式的原因码，不保存原始流、隐藏推理、响应正文或凭据到诊断。现有四次记录中丢失的原因和ID不补造。
