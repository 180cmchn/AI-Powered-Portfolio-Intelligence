# 第十六轮追加：断流的关闭顺序与处理方案

用户要求在完成原目标时调查断流，并提供“供应商判断请求方主动断开、与模型可用性无关”的信息。本调查把该信息作为重要线索；用户随后补充供应商侧断流时间：2026-11-04 23:48:05、2026-11-05 00:02:00、00:15:35（Asia/Shanghai），分别与A候选范围、A公共材料、A配置任务的本地异常秒级精确匹配；最后一次也与下述FIN抓取对应。尚未取得供应商原始日志或请求ID，因此这是时间相关性核对，不是完整供应商日志审计。不能把应用兼容错误码 `upstream_transport_error` 或异常名 `RemoteProtocolError` 直接解释成供应商责任或模型不可用。

## 已证实的边界

同一冻结源码 `b7afd986…` 的 environment 正常矩阵实际170次模型HTTP，165次 completed+EOF，5次收到HTTP200后未获完整终止对象。五次从最后一个**解码后的HTTP正文块**到异常分别为49.709、50.015、49.921、49.920、49.921秒。总耗时分别112.764、234.771、235.748、414.654、173.542秒，并不共享同一总请求期限。

各次300秒语义空闲、900秒请求硬限、父研究/子任务剩余期限均未到。记录没有用户取消、输入版本替换、停机或本地协议拒绝；后继任务创建与第一次正常停机都发生在失败之后。HTTPX出站网络读取为 `read=None`，活动连接不是空闲连接池项；已检查的请求链与已安装依赖中未发现50秒读取限制。见[生命周期核查](stream-disconnect-lifecycle-review.md)及[依赖与受控实验](local-stream-lifecycle-review.md)。这些事实不能单靠 `cancelled_by=null` 推导为“绝无任何本地关闭”。

第五次失败额外取得了真实包头时序，只观察本轮Python进程的两条指定连接，不采集正文或认证内容：

这一样本可以排除“项目研究任务首先主动关TCP”，并把可观察的关闭入口定位到本机代理一侧。它仍不能区分本机Mihomo主动结束与其转发外部节点/网关的关闭。前四次没有历史抓包，不能追认相同关闭方向。包头原件哈希、完整绑定和摘录见[关闭方向证据](tcp-close-observation.json)。

本机实际环境代理为127.0.0.1:7890，Mihomo v1.19.21、rule模式、TUN关闭；只读日志和连接API确认此供应商使用MATCH选中的代理链，非DIRECT。诊断未改变代理设置、系统CA、DNS或路由，未公开节点凭据。见[脱敏本机代理观察](local-proxy-observation.json)。供应商看见其下游断开，与“本机代理一侧先关闭”的观察可以同时成立，并不要求模型本身不可用。

## 受控区分与方案

本机受控实验分别触发客户端关闭、任务取消、应用空闲超时、代理空闲关闭、低层socket关闭，以及55秒静默后的正常HTTP/TLS终止。HTTP/TLS直连控制均能等待55秒并完成；代理关闭和低层socket关闭也能产生 `RemoteProtocolError` 且取消字段为空。因此异常类别本身不足以定位行为主体。普通 `client.aclose()`、任务取消和应用超时另有其可观察特征，不能与本案机械合并。临时证书仅用于实验进程，没有加入系统信任。

另通过已运行的Mihomo入口连接本机TLS夹具，先确认127.0.0.0/8规则与在途 `chains=[DIRECT]`，55秒正文静默后完整成功。该控制排除“本机入口普遍强制50秒断开”的解释，但不覆盖其外部代理节点路径；仅进程临时CA与子进程环境发生变化，系统和代理配置未变。

追加两条**无模型、无认证、无业务资料**的公共受控响应对照，每条仅请求两个星号字节且无重试。端点声明两字节间隔55秒，第二字节后再约55秒结束HTTP；实际为HTTP/1.1 chunked且无Content-Length，避免收到首字节就误判正文已经结束。environment在途代理链与前述供应商连接的两跳选择完全匹配：首字节0.632秒，此后50.040秒无正文即RemoteProtocolError，只收到1/2字节；direct首字节0.632秒，第二字节间隔54.999秒，再55.016秒后完整EOF，总110.647秒。两路均验证TLS/主机名。这是独立于模型的同类静默响应对照，支持问题位于当前所选代理传输路径的约50秒正文空闲边界，而不是必须依赖模型不可用才能出现。它仍不能指定Mihomo特定出站适配器、远端节点或中间设备中的唯一部件。完整证据见[代理空闲对照](public-idle-route-control.md)。这两条GET单独记录，不加入模型HTTP或模型费用分母。

当前可执行方案是通过已经实现的正常设置选择模型专用 `direct`，仅让模型/目录/能力检查不读取环境代理，保留TLS、主机名与环境CA。行情、PDF与系统代理保持原状。不增加超时、不关闭验证、不降低终止契约、不接受半截响应，也不将未知请求换线路暗中重发。TCP保活在本案已有效应答，单纯增大TCP keep-alive频率不是已经证实的解决办法；同理，盲目放大应用300/900秒时限无法解除另一层约50秒边界。

已在**新的独立数据库**通过正常manage.py/API入口显式选择direct，运行一次完整、有界业务矩阵，用于检验绕过该入口的实际效果。源码、角色/effort、任务40次上限和null输出上限与原矩阵相同；使用新任务身份，不重放旧未知请求。日常配置未变。它是方案效果验证；不同时间与模型自主研究意味着不是同payload随机对照，不能将后续成功宣称为唯一根因或永久稳定保证。中途路线证据见[direct运行快照](direct-route-runtime-check.json)，最终业务结果另行记录，不能把快照18/18完整当作全矩阵成功。

若业务必须保留代理路线，应继续沿实际代理节点逐跳核对应用数据空闲策略，并用相同的长静默受控响应验证配置，而非仅观察TCP保活或普通短请求。当前没有足够证据指定某个未见的50秒配置字段，更没有修改它。保留旧失败分母及响应关联ID后，供应商日志可用于进一步对齐下游关闭时间。

HTTPX的读取时限和连接池时限是不同概念，具体语义与本机0.28.1源码互相核对，依据[官方超时说明](https://www.python-httpx.org/advanced/timeouts/)和[官方trace扩展](https://www.python-httpx.org/advanced/extensions/)。主张仅限上述实测事实，没有据异常类别断言第三方模型可用性故障。
